# TartanOrder — engineering overview

TartanOrder is a voice/text campus-food prototype with deterministic, reversible order transactions. Gemini interprets requests; application code owns prices, requirements, edits and confirmation. There is no payment, purchase, POS call or kitchen dispatch. This document describes the implemented **API 2 / `cmu-meal-2026-09-12`** milestone. Verify that public `/api/health` reports this menu version and consult the release handoff for executed deployment evidence.

## One application, explicit responsibilities

One Next.js App Router app uses React, TypeScript, ordinary CSS and strict Zod contracts. Browser speech recognition produces a transcript; speech synthesis reads accepted responses or the immutable review. The controller owns one active capture/draft/request, cancellation, request IDs and revisions. The server uses verified `gemini-3.6-flash`; provider-only item codes translate through an exact dictionary into shared menu IDs. Gemini cannot provide authoritative prices, dietary evidence, computed cheapest meals or confirmation permission.

`Transcript or manual action → bounded interpretation → atomic engine → copied review → explicit simulated confirmation`

The eleven selected campus venues retain **237 priced configurations across eight venues** and **50 unavailable previews**. ScottyLabs supplies directory metadata/menu links, not item prices or measured waits. Prices come from CMU-hosted snapshots with source pages/hashes. The separate, selectable **fictional Demo Counter** has eleven illustrative items and explicit recipe evidence. Other archived venues remain unavailable through the public controller. Menu versions prevent replay from silently repricing an old order. See [dining-data.md](dining-data.md).

## Meal and dietary requirements

Optional meal mode selects one item per required main/side/drink component at one counter. A pure solver exhaustively enumerates supported configurations, retaining requested items, modifiers and locks. It ranks valid solutions by fewest changes to the accepted meal, then lower integer-cent subtotal, then stable IDs. A budget is a menu-subtotal limit, excluding tax, fees and meal-plan exchange assumptions. Infeasible changes leave the accepted cart and meal intact and produce at most two explicit choices. The UI shows the proposed items, subtotal and difference before acceptance.

One shared `checkCompatibility` function serves browsing, solving, manual/parsed edits, modifiers, wait substitutions, review and confirmation. Preferences, dislikes and allergies are distinct persistent fields. Results are **match**, **conflict** or **unknown** with reasons and provenance. Campus recipe/preparation evidence stays unknown where unverified. Fictional recipes record ingredient and preparation evidence separately; unknown cross-contact blocks allergy recommendations even when an allergen is absent from declared ingredients. Ambiguous/custom allergens remain explicit. Exact preference exceptions never waive allergies or subsequently added exclusions. The staff summary contacts nobody and cannot override missing evidence. [FARE guidance](https://www.foodallergy.org/resources/avoiding-cross-contact) informs that separation.

## Transaction boundaries

Every ADD creates a separate row. A batch validates against a temporary cart and applies atomically; ambiguous references require a targeted, revalidated choice. New input—including the first budget/allergy/dislike keystroke—invalidates review and pending decisions. Switching input surfaces discards the abandoned draft; stale, duplicate or cancelled replies cannot mutate the cart. Undo restores accepted cart/meal state while preserving the current dietary profile and rechecking restored food. Audit and revisions remain append-only/monotonic. New order clears profile and conversation.

Items can carry an unverified special request of up to 160 characters. Notes never change prices or dietary evidence, survive undo and same-item meal changes, and do not transfer to replacement food. Review copies all items, quantities, modifiers, notes and total. Confirmation requires that exact review and idle input, rechecks current requirements, and returns one idempotent simulated receipt. Fixed, explicitly seeded wait snapshots may offer a curated alternative; acceptance revalidates current meal/dietary constraints and noted items receive no swap suggestions. Detached replay uses recorded IDs/events/configuration with no ASR, HTTP or live confirmation. Explicit local exports include personal requirements and notes and warn before sharing.

## Evidence and limits

Notes-release evidence: **747 default tests passed / 29 opt-in skipped**, typecheck, lint and production build passed, with **34/34 browser checks**. Four real Gemini requests on the local production build covered per-item notes, a natural follow-up, a priced double burger and published campus fries. Review and receipt retained the notes; no fallback or page error occurred. [Recorded notes evidence](../evals/runs/item-notes-live-2026-09-12.json) uses synthetic typed inputs; mocked speech checks are not new human microphone proof. The property suite runs 1,000 sequences of up to 50 events with seed `20260912`; dedicated notes tests cover rollback, ambiguity, undo, snapshots, requirements and replay. These are test results, not formal proof or a language-accuracy benchmark. [integration.md](integration.md) records earlier milestones.

Node 22.23.2 and exact npm versions support local production and Vercel. Limits include five lines, ten units, quantities 1–5, eight operations and 1,500 transcript characters; server/client deadlines are 15/17 seconds with no automatic retry. Current register prices, stock, hours, tax and complete campus dietary suitability are unverified. State is browser memory; explicit export/replay is not persistence or a tamper-proof ledger. Browser validation establishes prototype correctness, not a production security boundary.

# TartanOrder — engineering overview

TartanOrder is a voice/text campus-food prototype with deterministic, reversible order transactions. Gemini interprets requests; application code owns prices, requirements, edits and confirmation. There is no payment, purchase, POS call or kitchen dispatch. The current main implementation uses **API 3 / `cmu-dietary-2026-09-12`** and combines runtime catalog/persistence, dietary marks, reversible special requests and language selection. Deployment and test records below include earlier releases; consult [the latest integration record](integration.md#main-integration--september-12-2026) and public `/api/health` for what is actually deployed.

## One application, explicit responsibilities

One Next.js App Router app uses React, TypeScript, ordinary CSS and strict Zod contracts. Browser speech recognition produces a transcript; speech synthesis reads accepted responses or the immutable review. The controller owns one active capture/draft/request, cancellation, request IDs and revisions. The server uses verified `gemini-3.6-flash`; provider-only item codes translate through an exact dictionary into shared menu IDs. Gemini cannot provide authoritative prices, dietary evidence, computed cheapest meals or confirmation permission.

`Transcript → controller → selected-menu interpretation → atomic engine → review snapshot → explicit confirmation → write-behind persistence`

The released catalog is data, not code: the server loads one immutable catalog version from Supabase at request time, validates it with the shared `Catalog` schema, and passes it to the client as props, into `createEngine`, into the parsers (which derive their lexicon per catalog) and into the UI through a React context. No runtime module imports the TypeScript catalog files; they remain the seed generator's input and the labelled `CATALOG_SOURCE=bundled` fallback.

The [ScottyLabs API](https://api.cmueats.com/v2/locations) supplies location metadata and menu links, **not item prices**. The public kiosk lists eight venues with 237 orderable configurations; the three requested venues that had only unavailable previews were removed from the selector on September 12, 2026 and remain archived. The separate, selectable **fictional Demo Counter** has eleven illustrative items and explicit recipe evidence for the meal and dietary demonstration. An internal catalog archive retains previous prices and regression fixtures but is blocked from public selection, HTTP requests and new cart operations. New snapshots include both directory-linked PDFs and CMU-hosted PDFs supplied by the user; source notes distinguish them. Each item records its location and source page; each source PDF records its hash. Prices are integer cents in an immutable, versioned catalog stored in Supabase and shared by server, engine and browser. A database trigger rejects any update or delete of published catalog rows; a price change is a new catalog version. Live API updates never reprice an existing cart or replay. See [dining-data.md](dining-data.md) for exact coverage and omissions.

## Meal and dietary requirements

Food evidence is catalog data. Each item row stores a `FoodEvidence` record: fictional, complete recipes for the Demo Counter; for campus items, ingredients inferred by the seed from the published name and description (provenance `inferred_campus`, completeness `partial`). Inference only adds ingredients, so it can add a conflict (detected meat, fish, dairy, egg, wheat, soy, nuts, sesame) but never certify absence; a published “veggie”/“vegan” wording is stored as a `dietaryClaims` entry that satisfies a preference and never an allergy. Modifiers are catalog data too: generated `no_<ingredient>` removals carry an `effect` that `foodEvidenceFor(menu, itemId, modifiers)` applies to the stored evidence, and the kiosk shows the resulting marks on every card and cart line, labelled as inferred.


Optional meal mode selects one item per required main/side/drink component at one counter. A pure solver exhaustively enumerates supported configurations, retaining requested items, modifiers and locks. It ranks valid solutions by fewest changes to the accepted meal, then lower integer-cent subtotal, then stable IDs. A budget is a menu-subtotal limit, excluding tax, fees and meal-plan exchange assumptions. Infeasible changes leave the accepted cart and meal intact and produce at most two explicit choices. The UI shows the proposed items, subtotal and difference before acceptance.

One shared `checkCompatibility` function serves browsing, solving, manual/parsed edits, modifiers, wait substitutions, review and confirmation. Preferences, dislikes and allergies are distinct persistent fields. Results are **match**, **conflict** or **unknown** with reasons and provenance. Campus recipe/preparation evidence stays unknown where unverified. Fictional recipes record ingredient and preparation evidence separately; unknown cross-contact blocks allergy recommendations even when an allergen is absent from declared ingredients. Ambiguous/custom allergens remain explicit. Exact preference exceptions never waive allergies or subsequently added exclusions. The staff summary contacts nobody and cannot override missing evidence. [FARE guidance](https://www.foodallergy.org/resources/avoiding-cross-contact) informs that separation.

- **Atomicity and ambiguity:** every ADD creates a separate row. All operations validate on a temporary cart; one invalid operation rejects the entire batch. Ambiguous rows require a targeted choice, revalidated before application. Unavailable independent items/options can be explanatory notices alongside valid edits; conditional requests clarify first.
- **Cancellation and Undo:** the controller owns capture, parsing, request IDs, revisions and cancellation. New input invalidates review; capture and parsing block confirmation. Cancelled, duplicate or stale replies cannot edit the cart. Location changes retain cart contents and discard old clarification context. Undo restores the accepted batch and referent while audit/revision advance.
- **Review and confirmation:** review copies the full order and total. Confirmation requires its exact ID/revision and idle input. Repeated confirmation returns the same receipt. Committed orders require a new session before editing.
- **Wait alternatives:** exact revision/snapshot-bound acceptance, stale-click rejection, suppression after decline/input, deterministic ranking and quantity-adjusted price differences are tested. Undo restores both the previous cart and its estimate. Unknown/stale live data cannot produce a faster claim.
- **Replay:** recorded events, permitted-venue policy, fixed wait configuration and IDs reconstruct a detached order without recognition, HTTP calls or live confirmation. Catalog versions must match; older menu logs are rejected instead of silently repriced. Pure engine code has no clock, network or randomness.
- **Persistence:** the session, every accepted audit entry and the receipt are written to Supabase behind the engine through a single in-flight write-behind chain. Duplicate entries are idempotent, a gap in the sequence is refused with 409, a failed write leaves the cart unchanged and shows a retry, and the server export replays to the identical view. Tests cover the route logic against an in-memory store and, when keys are present, against the project itself.

## Transaction boundaries

Every ADD creates a separate row. A batch validates against a temporary cart and applies atomically; ambiguous references require a targeted, revalidated choice. New input—including the first budget/allergy/dislike keystroke—invalidates review and pending decisions. Switching input surfaces discards the abandoned draft; stale, duplicate or cancelled replies cannot mutate the cart. Undo restores accepted cart/meal state while preserving the current dietary profile and rechecking restored food. Audit and revisions remain append-only/monotonic. New order clears profile and conversation.

Items can carry an unverified special request of up to 160 characters. Notes never change prices or dietary evidence, survive undo and same-item meal changes, and do not transfer to replacement food. Review copies all items, quantities, modifiers, notes and total. Confirmation requires that exact review and idle input, rechecks current requirements, and returns one idempotent simulated receipt. Fixed, explicitly seeded wait snapshots may offer a curated alternative; acceptance revalidates current meal/dietary constraints and noted items receive no swap suggestions. Detached replay uses recorded IDs/events/configuration with no ASR, HTTP or live confirmation. Explicit local exports include personal requirements and notes and warn before sharing.

## Persistence

Two server-only Supabase clients exist, both created from the current key formats and never from the legacy JWT keys. A **reader** built from the publishable key loads the five catalog tables (`catalog_versions`, `locations`, `modifiers`, `items`, `menu_previews`) under Row Level Security, which grants `select` to anonymous callers on those tables only. A **writer** built from the secret key bypasses RLS and is the only path to the three order tables (`sessions`, `audit_events`, `receipts`), which have no policies at all; the publishable key cannot read a single order row. Each loaded catalog version is validated through the shared `Catalog` schema, frozen and cached for the life of the process, because published versions are immutable: `BEFORE UPDATE OR DELETE` triggers raise `catalog rows are immutable; publish a new catalog version instead`, and `catalog_versions` may only change `is_active`. A partial unique index keeps exactly one version active.

Orders are written behind the engine. The controller creates the session (`POST /api/sessions`, bound to the active catalog version), then after every accepted audit entry enqueues the entries above the last acknowledged sequence number (`POST /api/sessions/[id]/events`, at most 200 per call), and saves the receipt once it exists (`POST /api/sessions/[id]/receipt`). One operation is in flight per session, later edits coalesce into the next batch, and ordering never awaits the network. Duplicates are acknowledged idempotently; a sequence gap is a 409; a failed call sets the kiosk badge to "Not saved to server" with a Retry button and leaves the cart untouched. `GET /api/sessions/[id]/export` assembles the stored session as an `ExportLog`, which the engineering panel can fetch and which `replayLog` reconstructs against the same catalog version. `ORDER_PERSISTENCE=off` disables the port and the badge reads "Server saving off". Bodies are bounded by the shared limits and validated with the V3 schemas before any database call; route logs never include transcripts.

The catalog is loaded through `CATALOG_SOURCE`: `supabase` (default) reads the active version through the reader and, on any failure, yields an explicit unavailable state that the page renders as a labelled panel with no menu; `bundled` serves the in-repo catalog and is labelled "Menu: bundled fallback" in the header, the engineering panel and `/api/health`. Bundled data never silently replaces a failed database load.
